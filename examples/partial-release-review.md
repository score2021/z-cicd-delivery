**r42 属于“部分目标已更新、尚未完成验收”**。`watch_timeout` 表明部署确认过程失败，不能据此判定更新未发生；现有快照已证明 api 更新到了 image-v2。

| 目标 | 断线后快照 | 状态判定 |
| --- | --- | --- |
| api | image-v2，updated=2、ready=2、available=2 | 已更新，就绪快照正常，尚未完成验收 |
| worker | image-v1，2 副本就绪 | 仍为旧版 |
| admin | image-v1，2 副本就绪 | 仍为旧版 |

目标 UID 未变、未发现其他 pipeline 覆盖，支持这是 r42 的部分更新；但缺少不可变镜像摘要、generation、配置和 schema 兼容性核对，尚不足以安全决定继续或回退。

**问题判定**

- 检查与镜像发布已通过，新版发布收据存在；失败发生在 deploy 阶段，api 更新之后的控制面连接／观察过程中。
- `watch_timeout` 的底层原因未知。现有材料不能区分网络中断、控制面问题或观察时限不足，也不支持直接延长超时作为修复。
- `/readyz` 出现 4 次 503，但没有采样总数、时间和实例对应信息，无法计算失败率或判定原因。
- 用户页面 30/30 成功，只支持该采样窗口内的页面请求成功；不能证明静态文件完整、业务任务成功或高可用。业务任务状态未知。

**首次失败处理的不足**

材料没有提供最初修复尝试，不能评价或编造具体操作。已知处理中的有效动作是取得同一变更窗口的只读快照，识别出了部分更新。

截至该快照，仍缺少：

- 原发布身份与逐目标 digest、generation、配置的完整对账。
- schema、状态及新旧组件混跑和恢复兼容性证据。
- 入口静态文件完整性与业务验收。
- `/readyz` 异常与用户请求之间按时间、来源、实例关联的诊断证据。

未开启自动回滚本身不能判为不足；兼容性未知时，自动回滚同样可能造成问题。

**最小恢复方案**

以下是后续恢复计划，本次未执行任何部署或外部检查。

1. **先对账。** 沿用 r42 的原 commit、pipeline、请求及镜像收据身份，重新读取三个目标的 UID、实际 digest、generation／observedGeneration、副本和配置，确认快照没有过期、没有新发布介入。
2. **再核兼容。** 确认是否执行过 schema 或数据变更，以及 image-v2 与 image-v1 混跑、回退的兼容性。兼容性未知时，保留部分更新状态，不盲目重跑整条流水线。
3. **按证据选择恢复方向：**

   | 条件 | 最小动作 |
   | --- | --- |
   | 新版及兼容性核对通过，决定继续 r42 | 保留已确认符合候选的 api；按脚本幂等规则，仅继续未完成目标 |
   | 决定回退，且旧版产物与数据兼容性已确认 | 仅将属于 r42 的 api 恢复到已核实的旧版摘要；worker、admin 无需重复更新 |
   | 归属、兼容性或实际状态仍未知 | 继续只读核对，保留未确认状态 |

4. 更新与验收使用同一部署锁；写入前再次核对目标版本，发生竞争即停止，避免覆盖后续发布。控制面观察可使用同一总预算内的有界查询，不凭超时盲目重发更新。

**验收步骤**

1. **产物与目标：** 核对发布收据、不可变 digest、来源、配置及逐目标 generation；确认所有目标符合所选继续或回退方案。
2. **组件状态：** 在明确窗口内检查副本与 readiness，记录 `/readyz` 总采样数、503 次数、时间、实例及原因；分别报告组件健康和用户成功率。
3. **真实入口：** 验证目标 TLS、路由和页面／API；按候选产物清单核对静态文件字节数与 hash，不能只看 HTTP 200。
4. **业务行为：** 在隔离环境或已有授权的无收费合成路径验证必要任务及结果；若没有可用路径，明确标记“未运行”，不创建收费任务。
5. **最终记录：** 保存 r42 各目标最终版本、验收窗口、结果和未决项。只有约定检查全部通过，才标记对应范围“验收通过”；回退能力与高可用仍需独立证据。
