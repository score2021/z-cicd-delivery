# 运维说明与问题复盘

## 运维说明交付内容

按实际范围记录：业务／发布两张路径图、发布触发与停止条件、阶段作业及证据、目标配置位置、变量对照、正常调整与恢复步骤、密钥有效期、未决事项。

变量对照表建议列：名称、当前脱敏值、源码默认、Type、Protected、scope、消费者、调整后需同步的位置。未访问到项目实际值时写未核对，不把源码默认当线上实际；File变量写正文类型和消费方式，不贴秘密。

命令注明在哪台角色主机、哪个目录、只读还是写操作，包含前置条件和实际副作用。镜像发布不必然应用副本／Secret／网络清单，不能让用户把整套初始化脚本当作改一个参数的命令。

## 复盘不是最终方案说明

从指定历史证据整理，至少保留如下因果：

| 字段 | 要回答的问题 |
| --- | --- |
| 问题／影响 | 卡在哪一步，谁受影响，有无外部副作用 |
| 首次可见现象 | 原job/request、时间窗、脱敏错误和观测 |
| 第一次处理 | 记录能够证明的首次行动，没有记录则写未知 |
| 为何失败／不足 | 根因证据、错误假设、只解决的一层；未确认另列 |
| 后续对照 | 改了什么变量、实际结果、撤销哪些试验 |
| 最终措施 | 修改点、验证或新路径、是否只是缓解 |
| 验证与限制 | 旧RED/新GREEN、负测、定向／全量／实际发布分层 |
| 对账／清理 | 原pending／unknown、各目标实际版本和自有资源清理 |
| 复用规则 | 下次最早在哪个小检查发现，什么条件下不适用 |

## 不混淆的类别

产品缺陷、测试自身错误、环境适配、安全门槛正确拒绝、部署前风险补强、用户暂停和未决网络现象分开写。不能把经验条目数说成生产事故数；不能用一次恢复覆盖此前失败，也不能虚构全部人工工时。

有多个因素同时变更，写组合通过；未证明某版本／供应商原因时不下定论。采用中继或远端探针后通了，应说明所绕开路径、信任变化、额外维护依赖，而不是“网络已经完全修复”。

## 完成标准

引用存在的证据，原失败可追溯；读者能区分当前正确操作、当时失败尝试和未来建议。文档不应嵌入内部链接、主机身份或代码用于公开分享；需要公开时重新写合成材料，原始手册留在原项目。
